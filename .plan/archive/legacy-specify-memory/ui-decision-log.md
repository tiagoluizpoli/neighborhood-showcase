| 2026-06-08 | Provedor block capability-based visibility | Provedor block shown based on role alone. | Provedor is capability-based: SYSTEM_MANAGER and ADMINISTRATOR do NOT see the Provedor block unless they independently hold a Provider Assignment with `enabled=true`. | 2026-06-08 | Backend architecture seam | Historical docs pointed at feature-sliced backend. | Backend is layered Clean Architecture — `presentation/`, `application/`, `domain/`, `infrastructure/`, `main/`. | 2026-06-08 | Provider Profile privacy enforcement | Provider Profile visibility setting not enforced on public seam. | Provider Profile visibility gates the entire public seam. | 2026-06-08 | Provider Profile reads must be pure | Provider Profile provisioning happened inside repository read methods. | Provider Profile provisioning must not happen inside repository read methods. | 2026-06-08 | Admin role parity | Administrator role not accepted on some global-admin routes where System Manager access is intended. | Administrator should be accepted wherever System Manager access is already intended, unless a route is explicitly more restrictive. | 2026-06-08 | Default export drift in production web | Production web code contains default exports mixed with named exports. | Default export drift cleaned up to align with repo's named-export rule. | Codebase aligns with conventions; bundle analysis and tree-shaking work correctly. | Approved; in PRD-v4. |
| 2026-06-08 | User/Provider separation | User was overloaded as both identity and provider capability. | `User` is the authenticated account root (Better Auth). `Provider` is a separate capability/relation, not a global user.role value. Global roles are `USER`, `SYSTEM_MANAGER`, `ADMINISTRATOR`. `MODERATOR` is condo-scoped, not a global role. | Identity and capability are cleanly separated; a user can exist without being a provider. | Approved; in PRD-v3. |
| 2026-06-08 | Provider Assignment as canonical relation | Previous terminology mixed location record and provider link. | `Provider Assignment` is the canonical name for the relation linking a provider to a condominium or address. Stores provider-operating context. `Provider Profile` is the canonical public-facing branding record (company name, logo, banner, public description, contact links). | Domain language is consistent across all code and documentation. | Approved; in PRD-v3. |
| 2026-06-08 | Backend composition root | No dedicated composition root. | Backend composition root lives under `src/main/` and owns bootstrap, app-router assembly, and dependency wiring. Infrastructure implementations own DB access and depend only on domain contracts. | DI is explicit and testable; bootstrap is centralized; wiring is auditable. | Approved; in PRD-v3. |
